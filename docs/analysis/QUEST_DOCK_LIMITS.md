# 用拓展坞把一切都接到 Quest：能做到什么、仍然做不到什么

> 前提：Quest 3 只有一个 USB-C，所有东西（采集卡、网卡、充电、键鼠）都得挂在同一个坞上，
> 共享 **USB 3.2 Gen1（5 Gbps）** 和**一档 PD 功率**。

---

## 1. 先明确：这个口能干什么

| 能力 | 支持情况 | 依据 |
|---|---|---|
| USB **主机**模式（挂外设） | ✅ | UVC 采集卡、U 盘、键鼠、**USB 网卡**都能枚举 |
| USB 3.x 数据带宽 | ✅ 5 Gbps 共享 | 所有外设分这一条 |
| PD 充电 | ✅ | 与数据共用；坞越复杂，充电功率越低 |
| **HDMI 输入** | ❌ **不支持** | 坞上的 HDMI 是**输出**口；Quest 没有 DP Alt Mode 输入 |
| HDMI 输入（曲线） | ✅ 需 **UVC 采集卡** | Meta 官方 *HDMI Link* 就是这条路 |
| **DisplayPort 输出** | ✅（v74 起） | 是"输出到外接显示器"，方向相反，对本项目无用 |
| USB 网卡（有线网络） | ✅ 多数可用（ASIX/RTL8153 类） | 社区实测可用；芯片型号要挑 |
| USB 串口（CH340/FTDI/CDC） | ❌ 无系统驱动 | 需要自研 App + USB Host 自己实现 |
| 后台服务 | ❌ 单一前台应用 | 切走即挂起 |

---

## 2. 拓展坞真正解决了什么

1. **同时供电 + 采集卡 + 有线网络**：不用在"充电"和"插采集卡"之间二选一
2. **有线网络替代 WiFi**：头姿上行 90 Hz 不再受空口抖动影响（但要和采集卡抢带宽）
3. **键鼠/存储**：调试时插 U 盘拷日志、插键盘输 URL

---

## 3. 仍然做不到的（按对本项目的影响排序）

### ① 浏览器和采集卡不能共存 —— 最致命

| 组合 | 结果 |
|---|---|
| WebXR 页面（ControlAnything）+ UVC 采集卡 | ❌ 一台头显只有一个前台应用 |
| 原生 App（Unity/Android）+ UVC | ✅ 但要自己写 App |

**这条是方案 A 的死穴**：走 WebXR 就没有 UVC 画面；要 UVC 画面就不是浏览器。
拓展坞完全无法改变这一点——它是应用模型的问题，不是接口的问题。

→ 走 WebXR 就必须让画面走 **IP（编码 → WiFi/有线 → `<video>`）**，这是 `docs/INTEGRATION_VIDEO_POSE.md` 的结论。

### ② 浏览器拿不到 UVC 摄像头

`getUserMedia` 在 Quest 浏览器里**不会枚举 USB 摄像头**；而且 Meta 不给第三方应用相机权限
（透视摄像头也不开放）。所以"页面里直接显示采集卡画面"没有任何 API 路径。

### ③ 不能当 USB 设备被别人读

Quest 不能把自己变成一块 UVC 摄像头/HDMI 源输出给别的机器——只能反过来。

### ④ 没有实时性

Android 是通用调度：线程唤醒抖动 **毫秒级**，USB 传输完成回调的时间也不确定。
所以 **1 kHz 控制环绝不能放在头显上**——这也是我们把闭环留在 F411 的根本原因。
头显只做"采样 + 上报"，容错靠 F411 的 150 ms / 1 s 保护。

### ⑤ 没有硬件时间同步

没有 PTP、没有 GPIO 触发、没有外部时钟输入。
视频帧和头姿帧只能**软件对时**（`requestVideoFrameCallback` 的 `expectedDisplayTime`），
误差 5~20 ms 量级，做不到帧级严格对齐。

### ⑥ 带宽与功率是零和的

```
4K60 采集（未压缩 ~6 Gbps / MJPEG ~1-2 Gbps）
+ 千兆网卡（满速 1 Gbps）
+ PD 充电（15~20 W）
─────────────────────────────────
共享 5 Gbps 和坞的功率上限
```

实测常见现象：开 4K 采集后网卡掉速、充电变慢、采集卡掉帧。
**1080p60 + 百兆级网络 + 65W PD** 是比较稳的组合。

### ⑦ 串口设备插不上去

想把 STM32 直接插头显调试？不行。CH340/FTDI 没有系统驱动，
除非自研 App 里用 `UsbManager` 手写协议栈。

### ⑧ 后台不可用

切应用 / 锁屏 → 页面挂起 → 头姿断流。对应我们已有的保护：
F411 侧 150 ms 冻结、1 s 停车。**这是必须存在的兜底，不是可选项。**

---

## 4. 结论：坞能改变"接线"，不能改变"应用模型"

| 你想要的 | 坞能帮 | 结论 |
|---|---|---|
| 供电 + 采集 + 网络同时在线 | ✅ | 坞的核心价值 |
| 有线网络替代 WiFi（降抖动） | ✅（挑对芯片） | 值得做 |
| 头显上同时看 UVC 画面 + 跑 WebXR | ❌ | 必须选一个 |
| 用头显做实时控制环 | ❌ | 留在 F411 |
| 插串口设备 | ❌ | 走网络/PC |

**所以两条路只能选一条：**

- **A（WebXR）**：画面走 IP 进浏览器，头姿走 WS。坞用来喂**有线网络**和供电。
- **B（原生 App）**：UVC 直采画面，头姿用 `OVRPlugin`。坞用来同时挂采集卡 + 网卡 + 充电。

A 的开发和迭代最快（改 JS 就生效），B 的延迟最低（少一次编解码）。
**本项目的既有代码已经把 A 的数据格式（16 B 帧）定好了，换 B 只需换"取样那一层"。**
