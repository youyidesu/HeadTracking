# 方案 A + 成品图传：整机链路分析

> 前提：头追走 **A（ControlAnything 的 WebXR 页面 → WebSocket → Node → UDP → C5 → SPI → F411）**。
> 本文分析它与成品图传拼在一起之后的**硬约束、延迟账、频谱冲突和落地顺序**。

---

## 1. 第一个硬约束：USB-C 只有一个工位

| 想干的事 | 需要什么 | 谁在用 USB-C |
|---|---|---|
| **图传画面进头显（UVC 采集卡）** | 原生 Android/Unity App + Camera2/USB Host | 占用 |
| **ControlAnything 头追（WebXR 页面）** | 浏览器前台 | 不占 USB，但要独占前台应用 |

**两者都是"前台应用"，一台头显同一时刻只能跑一个。**

所以"走 A"必然推出一个结论：

> **画面不能靠 UVC 采集卡进浏览器**——浏览器拿不到 UVC/USB 摄像头。
> 画面必须走 **IP 图传**（视频先编码，再进浏览器用 `<video>` / WebXR 视频层播放）。

这就是"结合成品图传"的核心：**图传从 HDMI+采集卡，改成 HDMI+编码器+WiFi+浏览器解码。**

---

## 2. 走 A 的完整链路

```
车体                                          操作端
┌──────────────┐   HDMI    ┌──────────────┐   WiFi    ┌──────────────┐
│ VRX/图传接收 │──────────►│ H.264 编码器 │──────────►│ Quest3 浏览器 │
│ （5.8G/数字）│           │ (或用带 IP   │           │ three.js 页面 │
└──────────────┘           │  输出的图传) │           │  ·视频层      │
                           └──────────────┘           │  ·XRFrame 头姿│
                                                      └──────┬───────┘
                                                             │ WebSocket(pose 16B@90Hz)
                                                             ▼
                                        ┌────────────────────────────┐
                                        │ 笔记本 Node（ControlAnything）│
                                        │  转发 pose → UDP            │
                                        └────────────┬───────────────┘
                                                     │ UDP(同 WiFi 或另一网卡)
                                                     ▼
                                        ┌────────────────────────────┐
                                        │ ESP32-C5 → SPI → F411       │
                                        └────────────────────────────┘
```

**注意这里有两个无线跳**：Quest↔笔记本、笔记本↔C5。这是方案 A 相对"直连 C5"多出来的成本，
下面 §5 给优化办法。

---

## 3. 图传选型与延迟账

| 图传形态 | 端到端（相机→头显显示） | 备注 |
|---|---|---|
| 模拟 5.8G + UVC 采集卡 | **40~70 ms** | 延迟最低，但必须原生 App（与方案 A 冲突） |
| 数字图传（DJI O3/Walksnail）HDMI + UVC | 70~110 ms | 同上，仍要原生 App |
| **数字图传 HDMI → 硬件编码器 → WiFi → 浏览器** | **60~150 ms** | **走 A 时的实际路径** |
| 车载直接 RTSP/WebRTC（相机就是 IP 相机） | 70~150 ms | 省掉 HDMI 环节，但整车级相机少见 |

**结论：走 A 之后，画面的端到端大概 60~150 ms，比"模拟+UVC"多 20~80 ms。**
这多出来的延迟直接体现在"甩头时画面里的景物跟不上"。

---

## 4. 云台与画面的对齐（最容易做错的一环）

设画面延迟 `T_video ≈ 100 ms`、头部角速度 `ω`：

```
画面里看到的云台指向，是 T-100ms 时刻的状态
云台实际已经指到 T 时刻的方向
=> 静止时完全对准；ω=200°/s 时，画面里差 20°
```

**这不是控制误差，是显示滞后**。三种应对：

| 做法 | 效果 | 代价 |
|---|---|---|
| **缩短 T_video**（降码率/降分辨率/硬件解码/选低延迟图传） | 最有效，线性收益 | 画质 |
| **HUD 用遥测画真实指向**（`qp_tele_t` 回传云台角度，前端按帧时间戳延迟渲染准星） | 让"准星 vs 云台轴"始终一致 | 要带时间戳的遥测 + 前端做延迟缓冲 |
| 训练"停头再打" | 零成本 | 人 |

推荐组合：**低延迟图传 + HUD 遥测准星**。协议里 `qp_tele_t` 早就留了，回传 50 Hz 就够。

---

## 5. 频谱：三方共存

| 占用 | 频段 | 与谁冲突 |
|---|---|---|
| 图传（模拟 5.8G） | 5645~5945 MHz | **与 WiFi 5G 高端 ch149-165 (5725-5850) 重叠** |
| Quest3 WiFi（走 A 必需） | 5 GHz / 6 GHz | 同上；Quest3 支持 6E 时最好 |
| 遥控（天地飞 2.4G） | 2400~2483 MHz | 与 WiFi 2.4G ch1-11 |

**规划建议：**

1. **Quest 用 6 GHz**（Quest3 支持 WiFi 6E 的机型/区域）——与图传、遥控彻底分层，最干净
2. 只能用 5 GHz 时：图传压在 **5645~5725（ch1~4）**，WiFi 锁 **5170~5330（UNII-1/2A）**，两者不重叠
3. 图传若支持选频，避开 WiFi 的 80 MHz 主信道
4. 遥控 2.4G 与 WiFi 2.4G 必须分离：**不要给 Quest 开 2.4G**

## 6. 带宽预算

| 流 | 帧/码率 | 占用 |
|---|---|---|
| 图传 1080p60 H.264 | 8 Mbps | 主体 |
| 图传 720p60 | 4 Mbps | 降级档 |
| pose（16 B × 90 Hz） | 1.4 kB/s | 可忽略 |
| 遥测（30 B × 50 Hz） | 1.5 kB/s | 可忽略 |
| ControlAnything 页面本身 | ~2 MB 首次加载 | 一次性 |

1080p60 + pose + 遥测 ≈ **8.01 Mbps**，Quest3 的 WiFi6 链路（数百 Mbps）毫无压力；
瓶颈在**空口竞争与抖动**，不在带宽。

---

## 7. 两跳无线怎么优化

方案 A 天然是 Quest→笔记本→C5。三个优化档：

| 档 | 做法 | 收益 |
|---|---|---|
| **基础** | 笔记本与 C5 都在同一 AP 下 | 可用，但两跳都走空口，抖动叠加 |
| **推荐** | **笔记本有线接车载 AP/交换机**（USB-Ethernet 或直接放车上） | 只剩 Quest→车 一跳无线，抖动减半 |
| **极致** | 把 Node 服务搬到车上（小型 Linux SBC 或 C5 自己托管裁剪页面） | 变成单跳，等价方案 C |

> 注意：C5 是 RISC-V 低配，跑不了完整 Node；但只是**托管页面 + WS 转发**的话，ESP32 的
> `httpd + websocket` 足够（页面几百 KB）。这条路等于"方案 A 的数据格式 + 方案 C 的部署形态"。

## 8. 降级与安全（与既有实现对齐）

| 事件 | 系统反应 |
|---|---|
| pose 断流 150 ms | 云台冻结（`app_gimbal.c` 已实现） |
| pose 断流 1 s | 两轴停车，进 FAULT |
| 图传断、pose 正常 | 云台继续跟随（盲跟），**HUD 提示无画面** → 建议同时降低最大转速 |
| WiFi 抖动（RTT > 50 ms） | 降帧到 45 Hz（`adaptiveDecimate` 打开） |
| 操作手按急停 | `QP_F_ESTOP` → 停车 + 锁存 |

**建议补一条**：图传状态也要并入安全判定——画面丢失时不允许高速甩头（操作手看不见后果）。

---

## 9. 落地顺序（把风险前置）

1. **先验图传进浏览器**：VRX/编码器 → 浏览器 `<video>` 能出画面、测出实际端到端延迟（手机慢动作拍"挥手"对比）
2. **再验 pose 通道**：ControlAnything 里 console 打点 → WS → Node → UDP → C5 → 串口打印
3. **合流**：页面里同时跑视频层 + pose 发送，测两路同时工作时的抖动
4. **上云台**：先低速（限 300 °/s），确认方向/符号，再解锁 150 rpm
5. **调 HUD**：遥测回传 + 延迟补偿准星

---

## 10. 与已有结论的关系

- **不改**：F411 侧协议只从 30 B 缩到 16 B；断连保护阈值、S 曲线、停靠逻辑全部沿用
- **要改**：Quest 端从"原生 Unity + OVRPlugin"换成"WebXR 页面 + `getViewerPose`"（本文 §2）
- **新增**：视频编码器 + 浏览器视频层（这是走 A 的入场券）
- **保留**：`qp_tele_t` 遥测回传，用于 HUD 准星
