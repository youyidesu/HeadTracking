# WiFi vs 蓝牙（BLE）—— 头姿链路选型对比

> 场景：90 Hz × 16 B 的 pose 帧，从 Quest/PC 送到 C5；赛场 2.4G 遥控密集、5G 也有图传与人群设备。

---

## 1. 一句话结论

| | WiFi 5G（UDP/ESP-NOW） | BLE 5 |
|---|---|---|
| 抗干扰方式 | **被动**：CSMA 退避，不换信道 | **主动**：自适应跳频 AFH，1600 跳/s，自动拉黑坏信道 |
| 延迟特性 | 平均低，**抖动大**（拥挤时 10~50 ms） | 平均略高，**抖动小**（由连接间隔决定，可预测） |
| 频段 | 5 GHz（避开 2.4G 遥控） | **只有 2.4 GHz**（和遥控同频） |
| 带宽 | 充裕 | 够用（11 kbps 需求 vs 数百 kbps 可用） |
| 复杂度 | AP / IP / 端口 | GATT 服务 + 配对 |

**你问的"主动避开拥挤信道"，BLE 天生就有，WiFi 没有。**

---

## 2. BLE 的自适应跳频到底做了什么

| 项 | 值 |
|---|---|
| 跳频速率 | **1600 跳/秒**（每 625 µs 换一次） |
| 信道数 | 40 个 × 2 MHz（37 数据 + 3 广播） |
| AFH 机制 | 链路层持续统计各信道质量，**把被占用的信道拉黑**，只在剩余信道里跳 |
| 效果 | 遇到窄带干扰（模拟图传的边带、遥控的 FHSS）时，会自动绕开那几条 |

这是链路层的自动行为，**应用层一行代码都不用写**——正好解决你上一个问题里
"ESP 做不到实时避开拥挤信道"的痛点（WiFi 侧确实做不到）。

---

## 3. 延迟与容量：能不能扛 90 Hz

| 参数 | 计算 | 结论 |
|---|---|---|
| 连接间隔 | 最小 **7.5 ms**（BLE 4.2+） | 133 次事件/秒 → 90 Hz 有余量 |
| 单次事件载荷 | ATT MTU 默认 23 → 20 B 有效 | 16 B 一帧正好塞下 |
| 延迟（平均） | 间隔/2 + 处理 ≈ **4~6 ms** | 与 WiFi 相当 |
| 延迟（最差） | 1.5 个间隔 ≈ **11 ms** | **比拥挤 WiFi 稳得多** |
| 吞吐需求 | 90 × 16 B = 1.4 kB/s = **11 kbps** | BLE 1M/2M PHY 下占用 <5% |

**BLE 的延迟不是更低，而是更"可预测"**——这对闭环控制反而更重要。

---

## 4. 和 WiFi 的逐项对比

| 维度 | WiFi 5G | BLE 5 |
|---|---|---|
| **抗 2.4G 遥控** | ✅ 不同频段 | ⚠️ 同频段，靠 AFH 绕 |
| **抗 5.8G 图传** | ⚠️ 取决于选信道（ch36-48 可避） | ✅ 不同频段 |
| **抗人群遮挡** | 5G 衰减大，需抬高天线 | 2.4G 绕射稍好，但衰减同样明显 |
| **延迟抖动** | ❌ 拥挤时 10~50 ms | ✅ 锁在连接间隔内 |
| **测距/穿墙** | 5G 差 | 2.4G 稍好 |
| **免 AP** | ESP-NOW 可以 | ✅ 天然点对点 |
| **多设备** | 多 | 一个中心最多 7 个外设，本场景 1 个够 |
| **功耗** | 高 | 低 |
| **工程复杂度** | 中（AP/IP/端口） | 中（GATT/配对） |
| **头显原生支持** | WebXR 里只能走 WebSocket（要 PC/AP） | Quest 浏览器支持 **Web Bluetooth**（需实测） |

---

## 5. 一个容易被忽略的组合拳

**WiFi 走 5G + BLE 走 2.4G 同时开**——听上去完美，但 **C5 是单射频**，
WiFi 在 5 GHz 时射频不在 2.4G，两者只能时间片共存（ESP-IDF 有 RF Coexistence 机制，
但会互相打断）。

**必须实测**：`esp_coex_...` 打开后，5G WiFi 与 BLE 同时工作的实际吞吐/丢包。

更稳的做法：**二选一**，而不是硬凑双链路。

---

## 6. 推荐

| 场景 | 选择 |
|---|---|
| 赛场 2.4G 遥控极密集、5G 相对干净 | **WiFi 5G（ch36-48）** |
| 现场没有可靠 AP、也不方便架 | **ESP-NOW @ 5G**（若实测可用）或 **BLE** |
| 想要"自动躲干扰"且能接受 2.4G | **BLE**——AFH 是真·自动避让 |
| 需要极低抖动、有确定性 | **BLE**（连接间隔锁死） |
| 需要高带宽/图传 | WiFi（BLE 做不到） |

**我的排序（针对你这个项目）**：

1. **ESP-NOW @ 5G**（如果实测能跑）—— 免 AP + 5G 避遥控 + 2~5 ms
2. **WiFi 5G UDP**（ch36-48）—— 成熟、可控、有 AP 就行
3. **BLE** —— 抗干扰最聪明，但只能 2.4G，和遥控抢频
4. **ESP-NOW @ 2.4G** —— 最容易受遥控影响

---

## 7. 如果要试 BLE，需要确认的两件事

1. **Quest 浏览器是否支持 Web Bluetooth**（`navigator.bluetooth`）——支持的话头显可以直连 C5，
   连 AP 和 PC 都省了；不支持就得走原生 App。
2. **连接间隔能不能压到 7.5 ms**——Android 侧通常可以请求，但系统可能强制 ≥15 ms
   （不同厂商策略不同），这会直接把延迟抬到 10~20 ms。

这两条不确认，BLE 的"低抖动"优势就落不了地。
